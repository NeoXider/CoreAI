## Acceptance review

- **Distinct maximum matching:** read the entire checker, rule model and public tool wrapper. The new search finds an augmenting path for each rule requirement; exact ingredients and registered groups are edges, with every requirement consuming one separate ingredient. It can reassign a broad group away from a later exact requirement. Existing size-sorted rule selection, weighted scores, blocking/bonus reasons and custom validators are unchanged. The wrapper preserves duplicate ingredient entries instead of applying a distinct-name filter.
- **Matching capacity and work:** a prior rule owns at most one ingredient. An ingredient is predecessor-marked once per search, so that assigned rule can enter the pending queue at most once. At augmentation `r`, at most `r` prior matched rules plus the new root can be queued; the `ruleElements.Count` array is sufficient. Path reconstruction follows each rule's previous ingredient back to the unmatched root. The implementation is iterative with linear auxiliary storage, not factorial backtracking or unbounded recursion. Its edge scanning is polynomial (worst-case O(R squared times I) for R requirements and I ingredients); no fixed caller-input maximum or measured latency is claimed. The existing rule contract is exact element/registered group names, not a newly introduced wildcard language or a separate recipe solver.
