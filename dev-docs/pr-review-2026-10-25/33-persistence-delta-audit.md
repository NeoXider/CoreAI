## Confirmed introduced findings

### DELTA-PERSIST-001 [P2] Publish an actual history trim even when persistence arming refuses the completed append

**Changed anchor:** `Assets/CoreAiUnity/Runtime/Source/Features/AgentMemory/Infrastructure/FileAgentMemoryStore.cs:1153-1154`.

**Concrete trigger:** a WebGL host without automatic `persistentDataPath` persistence has a `FileAgentMemoryStore` with a one-message cap and an existing message. Subscribe to `HistoryTrimmed`, then call `AppendChatMessageAsync` with `persistToDisk: true` and another message. This is the store's explicitly supported refusal path: file I/O reaches the in-memory filesystem, while `CoreAiWebGlPersistence.SyncAsync` returns false. No custom identity, cross-process race, invented account lifecycle or failed append I/O is required.

**Expected/actual:** the async operation must still fail with its durability IOException, and the host must receive the trim that already changed the actual cache/history window. The type documentation promises an event on every trim (lines 71-75, 308-311); `TrimRetained` defines loss from the visible window as the trim that reaches the event (lines 1320-1323). The candidate now throws before publishing the event, so the host never learns through its subscribed event that an earlier turn was dropped. The existing trim log may still appear; this finding concerns the promised notification surface, not universal silence.

**Causal path:** `AppendLineCore` trims its candidate at line 1212, successfully writes the row, advances the revision and publishes the new cache at lines 1233-1251, then returns `Wrote = true`. New line 1153 awaits `SettleAsync` before line 1154 calls `RaiseTrimmedAsync`. `SettleAsync` throws the false-arming IOException from `ConfirmDurableAsync`, so `RaiseTrimmedAsync` is skipped. At HEAD, the same async append raised the trim after releasing locks and then performed confirmation; it delivered the event even though the caller received the same IOException. This ordering change is unrelated to whether a migration happened and therefore also affects ordinary appends.

**Repair direction:** settle observed writes without losing a completed trim notification, preserving the original durability error and caller-context callback behavior. Do not report a successful durable append and do not publish a trim for an append that never changed the accepted history/cache. Keep callbacks outside both storage gates.

**Meaningful regression:** execute the append through a WebGL configuration where the real arming port returns false, or root's bounded test lane for that existing port. Assert IOException, exactly one trim event on the captured context with the correct dropped/retained counts, and the actual newest history row. Retain `AsyncHistoryTrim_MarshalsCallbackToCallerAfterReleasingStorageLocks` and successful trim controls. Current Editor tests always receive true from the production arming port, so their success cannot cover this branch. This worker ran no browser or fault reproduction; the conditional source path and HEAD ordering were inspected directly.

### DELTA-PERSIST-002 [P2] Retain the admitted append operation until its caller-context callback settles

**Changed anchor:** `Assets/CoreAiUnity/Runtime/Source/Features/AgentMemory/Infrastructure/FileAgentMemoryStore.cs:1120-1154`, specifically the new using-block exit at line 1151.

**Concrete trigger:** use the existing `HeldSynchronizationContext` pattern from `AsyncHistoryTrim_MarshalsCallbackToCallerAfterReleasingStorageLocks`. Seed a one-row-cap store, start a trimming async append from that context, and wait until its trim notification is posted but deliberately not executed. The append Task is still pending. Call `Dispose` before releasing the callback. This is reproducible in Editor/Standalone with ordinary successful arming, including a transient append, and needs no browser or custom persistence API.

**Expected/actual:** the public Dispose contract at lines 1953-1959 says owned caches are released after every admitted operation settles. `ResidentHistoryCount` should therefore remain one while that already admitted append is still pending, then become zero after its callback/task completes. The candidate prematurely releases the cache/path ownership during Dispose while the admitted Task still awaits its callback; `ResidentHistoryCount` becomes zero before completion.

**Causal path:** `GetMutationGate` increments `_activeOperations` at line 1882. The new block disposes `MutationLease` at line 1151, which calls `ExitOperation` at line 1905, before awaiting `RaiseTrimmedAsync` at line 1154. A held entry context makes that notification await genuinely pending (lines 1421-1434), while `_activeOperations` is already zero. Dispose can then call `ReleaseResources` and clear the history/path leases immediately. At HEAD, the using declaration remained alive through the callback and confirmation; its gates were explicitly released first, but operation ownership remained until the method settled.

**Repair direction and regression:** restore admitted-operation ownership through notification/confirmation while releasing both storage gates before any host callback. Extend the held-context test to assert pending Task plus one resident partition, dispose, assert ownership is retained and new calls are rejected, prove a healthy peer can still acquire the released path gate, then release callbacks and assert one event, successful admitted completion and zero resident partitions. The test's event handler should observe captured event data rather than start new operations on the disposed store. This is a concrete observable lifecycle-contract failure; corruption, invalid semaphore access and an exception in the admitted append itself are not claimed or required. Root accepted this scope during the audit; no implementation or execution was done here.
