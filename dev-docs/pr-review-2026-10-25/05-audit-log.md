### PR-AUD-001 [P2] Strict audit encoding rejects a normal diagnostic snapshot and repeatedly requeues its whole batch

- Changed anchor: `Assets/CoreAiUnity/Runtime/Source/Features/Audit/AuditLogWriter.cs:889`, replacing the previous `new StreamWriter(path, true)` with an explicit strict `new UTF8Encoding(false, true)`.
- Concrete valid scenario: a normal successful tool returns `new string('a', 1999) + char.ConvertFromUtf32(0x1F600) + "z"`. The full 2002-code-unit result is valid Unicode and is below the default main tool-result cap. Native MEAI result marshalling receives valid text. With the default `LogToolCallResults = true`, the later `ToolExecutionPolicy.SafeResultJson` at line 1334 cuts the already-marshalled result to 2000 UTF-16 units, leaving the emoji's high surrogate at the end. No malformed model input or unsupported host configuration is required.
- Exact in-repo route after that cut: `ToolExecutionPolicy.cs:959` calls `MessagePipeToolCallEventPublisher.PublishCompleted` (injected by `MeaiLlmClient.cs:620-623`, and in batch by lines 201-204 via `SmartToolCallingChatClient.cs:350-351`). `MessagePipeToolCallEventPublisher.cs:38-41` creates the event and directly calls `CoreAi.NotifyToolCallCompleted` before its global-broker readiness check. `CoreAi.cs:802-812` raises `OnToolCallCompleted`; `AuditLogInstaller.cs:13,18` resolves the subscribed `ToolCallAuditInterceptor`, whose lines 27-39 pass `evt.ResultJson` into `AuditEntry.ResultDetail`. No result marshaler runs between this post-marshalling cut and the audit writer.
- Expected: the existing diagnostic snapshot remains writable on the supported Unity runtime, and healthy accepted records cannot be indefinitely held behind one normal tool-result snapshot. Any text normalization must agree with hash preimages and must not acknowledge an unsuccessful append.
- Actual and causal source path: Newtonsoft leaves the lone surrogate literal in the serialized audit text. The PR's strict encoder throws `EncoderFallbackException` during writing/flushing/disposal. Append handling at lines 913-940 correctly restores the original byte length, then rethrows. `FlushBatchCore` at lines 834-839 consequently requeues the entire unchanged batch. Subsequent worker flushes repeat the same content failure, leaving later healthy entries unwritten until the poison record is evicted or pending state is discarded. Rollback success leaves no quarantine for the recovery API to clear.
- Introduced behavior is runtime-specific and verified against the actual Unity Mono baseline, not guessed from modern .NET defaults. The root's `artifacts/pr-review-20261025/audit-surrogate-baseline-mono.txt`, executed with `D:/unity/Editor/6000.6.0f1/Editor/Data/MonoBleedingEdge/bin/mono.exe`, reports `CLR=4.0.30319.42000;fallback=System.Text.EncoderReplacementFallback` and `BASELINE_WRITE=success` for the prior constructor and the truncated value. Some other BCLs may choose a different default; this finding concerns the supported Unity Mono path.
- Final same-process comparison: the root's `artifacts/pr-review-20261025/audit-surrogate-mono-comparison.txt` reports the same CLR/replacement fallback, `STRICT_WRITE=System.Text.EncoderFallbackException`, and `BASELINE_WRITE=success`. This reviewer read both that receipt and `C:/AI/work/coreai-pr-review-20261025/Utf8BaselineProbe.cs`: the program loads the installed Newtonsoft DLL, serializes the same truncated value, and tests the old and explicit-strict `StreamWriter` constructors in one Mono process. This is a serializer/writer-primitive comparison, not a full `AuditLogWriter` regression run.
- Additional exact serializer/encoder evidence read directly: `artifacts/pr-review-20261025/audit-surrogate-serializer-probe.json` used the installed Unity Newtonsoft DLL, SHA-256 `7292D3EB508652D14726749DD27094F2D481AECCF2DB6427B62F68A71460897E`; it records a valid input length of 2002, a truncated length of 2000, final code unit 55357, a raw high surrogate surviving serialization, and `System.Text.EncoderFallbackException` under the explicit strict encoder.
- Minimal meaningful regression plan: execute the real tool-policy/publisher/interceptor path with the valid boundary result, place healthy audit entries before and after it, and flush/retry. Require the intended normalized snapshot and all accepted healthy entries once in a verifier-valid chain. Exercise a writer-disposal flush as well as ordinary retry, and preserve the existing exact rollback/quarantine assertions. Compare against the actual Unity Mono baseline instead of assuming another runtime's `StreamWriter` defaults.

The repeated-batch consequence is a source-confirmed control-flow result; full writer, live Editor, IL2CPP and WebGL reproduction are not claimed. The protected main `MaxToolResultChars` cut at line 936 is not the source of the invalid snapshot; the separate later 2000-character audit cut is.

### PR-AUD-002 [P3] New Mods log clipping splits valid Unicode surrogate pairs

- Changed anchor: `Assets/CoreAIMods/Runtime/Logging/LuaLogService.cs:278`, adding a raw UTF-16 `Substring` before the truncation marker.
- Concrete valid scenario: construct `LuaLogService` with `maximumMessageCharacters: 16` and append a message `"a" + char.ConvertFromUtf32(0x1F600) + new string('x', 20)` for mod `m`. All input text is valid Unicode and the configuration is supported. The marker `...[truncated]` is 14 code units, so the new clamp retains two prefix code units: `a` plus the emoji's high surrogate, excluding its low surrogate. The same issue affects `ScriptName` because both fields call `Clamp`.
- Expected: clipping valid text preserves valid Unicode while respecting the cap and retaining the marker. Here the retained prefix must stop before the whole surrogate pair when the pair cannot fit.
- Actual and causal source path: `Append` assigns the malformed clamp result at lines 110-111, stores a copy at line 118, and `Query` returns another copy at line 203. The returned text contains `a`, code unit `0xD83D` without its matching low surrogate, then `...[truncated]`. `LuaLogFormatter` and the direct `GetModLogsLlmTool.ExecuteAsync` JSON surface preserve that malformed string, producing replacement/error behavior for consumers rather than a valid clipped character sequence.
- Introduced behavior: the old service retained this short valid message intact. The new cap/marker feature creates the invalid sequence. This is an observable output defect in the service itself; it does not depend on assuming a changed default `StreamWriter` encoding or on a hypothetical native-audit path.
- Supporting executed evidence, performed by the root and read by this reviewer: `artifacts/pr-review-20261025/audit-surrogate-serializer-probe.json` loaded `Newtonsoft.Json, Version=13.0.0.0` from `Library/PackageCache/com.unity.nuget.newtonsoft-json@4dfd81071c64/Runtime/Newtonsoft.Json.dll`, SHA-256 `7292D3EB508652D14726749DD27094F2D481AECCF2DB6427B62F68A71460897E`. For an analogous valid-string cut it records `lastTruncatedCodeUnit: 55357`, `serializedContainsRawHighSurrogate: true`, and strict UTF-8 encoding failing with `System.Text.EncoderFallbackException`. That probe does not execute `LuaLogService` or the complete writer.
- Minimal meaningful regression plan: exercise both message and script-name clipping with a pair spanning the retained prefix; assert well-formed Unicode, a bounded length, and the marker in `Query` results. Include a complete-pair/ASCII control and encode the direct formatter/`ExecuteAsync` result with strict UTF-8 to ensure the clip introduces no invalid code unit. Keep identity, retained-character bounds and copy-isolation assertions intact.
- Uncertainty and scope: the split follows directly from the exact code-unit indices. This reviewer ran no probe/test. No audit queue stall or file loss is counted for this separate clamp finding: native MEAI result marshalling may normalize this value before it reaches an audit event.
