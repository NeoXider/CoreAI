## Confirmed actionable findings

### HUB-001 — P2 — World Loads becomes permanently inactive after disabling and re-enabling the Hub (new)

- Evidence: `Assets/CoreAIMods/Runtime/HubIntegration/HubModsPages.cs:121` creates one page and `:127` registers a factory returning that same instance. `Assets/CoreAIHub/Runtime/CoreAiHubWindow.cs:146` calls `DestroyAllPages` on disable; `:802` calls each cached page's `OnDestroyed`. `HubModsPages.cs:205` permanently marks the confirmation page destroyed, pauses its schedule, and unsubscribes. `:219` returns its cached root on subsequent construction; neither activation (`:193`) nor construction clears that state or subscribes again. Decisions (`:640`), refresh (`:429`), and autosave requests (`:554`) refuse destroyed pages.
- Trigger and impact: let the window resolve its registered pages, disable and re-enable its component/GameObject with the same registry, then open World Loads or queue a load. The factory supplies the destroyed page, so requests no longer draw attention and load/reset decisions stop working until registration/scene reconstruction. This is component disable, not ordinary Hub collapse.
- Confidence: high; direct lifecycle and guard analysis, not an interactive reproduction. The registry/window lifecycle is owned here; world-runtime internals need not change.
- Existing guards/tests: destruction is intentionally idempotent; that makes reuse fail permanently. `Assets/CoreAIMods/Tests/EditMode/CoreAiModsHubBinderFullTierEditModeTests.cs:197`, `:236`, and `:709` exercise fresh pages and one teardown, but not registry-factory reuse after window teardown.
- Fix direction: make page instances window-lifetime objects while keeping attention subscription ownership explicit, or define and implement a supported rebind lifecycle. Do not simply revive an old page while its previous async decisions may still be completing.
- Regression: register through `RegisterWorldLoadConfirmation`, attach a real test panel/window, disable/re-enable it, then queue and reject/confirm a request exactly once; check attention subscription count, reset behavior, and disposal during an outstanding decision.

### HUB-002 — P2 — Replacing a window registry retains pages from the previous host (new)

- Evidence: `Assets/CoreAIHub/Runtime/CoreAiHubWindow.cs:109` swaps subscriptions/registry then calls `RebuildTabs` at `:118`, without destroying cached pages/content. Pruning (`:513`) removes only IDs absent from the new list. Metadata (`:547`), page resolution (`:664`), and content (`:693`) reuse caches by ID alone. The active page is refreshed at `:504`, not reconstructed from the new registry.
- Trigger and impact: assign registry A, render a page, then assign registry B containing the same page ID but a factory connected to another settings/world/service scope. The tab still renders and invokes A's page and retains A's listeners; B's replacement factory is ignored. This violates the public runtime host/registry replacement seam and can send later UI actions to a previous session.
- Confidence: high; deterministic cache/call-chain defect established by inspection. No runtime test executed.
- Existing guards/tests: same-registry assignment is intentionally ignored, and event-based re-registration explicitly destroys the old page (`:444`), but the different-registry setter misses that invalidation. `Assets/CoreAiUnity/Tests/EditMode/HubPageRegistryEditModeTests.cs:24` covers replacing factories inside the registry only. `CoreAiHubWindowEscapeEditModeTests.cs` covers injected active pages and Escape, not registry replacement.
- Fix direction: tear down the old registry's page instances/content before the swap, preserve only an active ID when appropriate, and fence queued old-registry callbacks with a registry/rebuild generation.
- Regression: use A/B registries with identical IDs and separately recorded factories/lifecycle/actions. Assert A is deactivated/destroyed once, B is built/activated, clicks reach B, and an already queued A event cannot destroy B's replacement.

### HUB-003 — P2 — Mod CRUD can report success after the backing store refuses the change (new Hub finding)

- Evidence: `Assets/CoreAIMods/Runtime/HubIntegration/HubModServiceBase.cs:322` unloads before attempting deletion; `:325` calls the store, `:327` swallows exceptions, and `:332` returns true. `Assets/CoreAIMods/Runtime/HubIntegration/HubModsPage.cs:413` ignores the service's boolean result and displays `Deleted`. The same boundary suppresses save errors in `HubModServiceBase.cs:478` and active-flag failures at `:591`, while `:248` returns a normal `HubModSaveResult`, whose `Describe` claims `Saved & ran` (`IHubModService.cs:103`).
- Trigger and impact: a replaceable `ILuaModSourceStore` throws on Delete/Save/SetActive (permission loss, quota failure, or an explicit refusal), or a replacement `IHubModService.Delete` returns false. Delete can stop the live mod but retain its stored package and still report success; it can return on restart when its active flag also remains true (for example, a Hub-only store or failed active-flag write). Save may run a new version while the store retains the old one. These UI outcomes are wrong even when the lower layer correctly reports failure.
- Confidence: high for the Hub's suppression of explicit failures. This does not claim every production first-load path accepts a refused save: the world-session facade has a source-kept guard (`Assets/CoreAIMods/Runtime/Infrastructure/RbxWorldPackageContracts.cs:4342`); the registered direct-runtime overload and reload/delete paths still expose the Hub defect. Null-store compositions should explicitly distinguish running from saving.
- Existing tests: the in-memory store in `Assets/CoreAIMods/Tests/EditMode/CoreAiModsHubBinderFullTierEditModeTests.cs:881` always accepts Save/Delete; `:1047` intentionally verifies the supported configuration where the Hub writes a store the runtime does not write. There is no refusal assertion in these Hub tests.
- Fix direction: propagate persistence outcomes through the service/result and UI; preserve the distinct live/durable state when runtime mutation already happened. Honor Delete's return value and keep failed operations retryable. Underlying file-store durability/error handling belongs to report `05-mods-runtime-sandbox.md`; this report owns only Hub receipt/suppression behavior.
- Regression: use a fake store that throws separately on Save, Delete, and SetActive, plus a replacement Hub service returning false from Delete. Assert no success status, retained/removed data and live state are described accurately, and retry succeeds after recovery. Include a Hub-only source store and a world-session facade so the existing first-load guard is preserved.

### HUB-004 — P2 — An open mod draft silently overwrites a newer AI/host edit (new)

- Evidence: `Assets/CoreAIMods/Runtime/HubIntegration/HubModEditorPage.cs:116` snapshots the initial source; `:302` later passes only ID and buffer text to `SaveOrReload` at `:313`, without checking the current source/revision. `Assets/CoreAIMods/Runtime/HubIntegration/HubModsPage.cs:553` explicitly ignores source-change notifications while the editor is open. There is no conflict/dirty state in the editor. Closing invokes the callback directly (`HubModEditorPage.cs:462`), which clears the only editor tree (`HubModsPage.cs:543`).
- Trigger and impact: open version A, edit the local draft, let `manage_mods` or another host/editor save B, then click Save & run. The old draft replaces and executes over B without warning. This requires only interleaved main-thread actions, not simultaneous execution. Back or window teardown also discards an unsaved draft without a preserve/discard choice. Revision history can sometimes recover a saved B; it does not prevent the unintended replacement or recover a never-saved draft.
- Confidence: high for the lost-update and discarded-buffer paths; no interactive UI reproduction performed. The generic lost-update TODO at `TODO.md:3231` names other stores, not this Hub editor path.
- Existing guards/tests: deferring ModsChanged refresh deliberately protects the currently typed buffer from being replaced; it does not protect the saved source. `Assets/CoreAIMods/Tests/EditMode/LuaSyntaxHighlighterEditModeTests.cs:320` and `:347` exercise reload mode/preferences and success status, not two writers or dirty-buffer closure.
- Fix direction: keep a base source fingerprint/revision and detect conflicts before mutation; offer reload, explicit overwrite, or copy/merge while preserving the draft. Track dirty state and preserve/confirm discard on Back and host teardown according to a documented host policy. A storage-level compare-and-swap seam is needed for cross-thread writers.
- Regression: A opens, draft A changes, B is saved externally, then A attempts Save. Assert B stays live/stored until an explicit overwrite decision and A's draft survives the conflict. Cover Back, failed Save, disable/re-enable, and two editor instances.

### HUB-005 — P2 — World-load failures are overwritten before the result can be read (new)

- Evidence: `Assets/CoreAIMods/Runtime/HubIntegration/HubModsPages.cs:699` writes a failed result and `:707` writes exceptions to `_status`; the unconditional `finally` at `:714` calls `Refresh(false)`, which rewrites the same label at `:473`. The persistent `_outcome` label (`:236`) is used for successful loads/startup outcomes, but not failed decisions. Autosave request exceptions at `:578` are similarly replaced on the periodic refresh (`:272`). The production service consumes a confirmation before loading (`Assets/CoreAIMods/Runtime/Infrastructure/RbxWorldPackageContracts.cs:1821`) and returns failure for expired/unknown tokens (`:1815`).
- Trigger and impact: a player confirms a request that expired, or confirmed loading fails after its token is consumed. The failure is immediately replaced by `No pending requests` (or the unrelated remaining-request prompt), with no durable outcome text. The player cannot distinguish failed loading from a completed decision. A failed autosave request also loses its diagnostic on the next one-second refresh.
- Confidence: high; the failed decision's overwrite is in the same continuation and needs no timing race. No Unity/UI execution was performed.
- Existing tests: `Assets/CoreAIMods/Tests/EditMode/CoreAiModsHubBinderFullTierEditModeTests.cs:197` deliberately checks the empty status after rejection; `:643` checks persistent success/startup-persistence outcomes. Neither asserts a failed confirmation's visible outcome.

- Regression: return a failed `RbxWorldLoadResult`, throw during confirmation, and expire a token between rendering and click. Assert the exact failure remains after `finally` and later refresh ticks; a successful subsequent decision may replace it. Also fail autosave requesting and verify the failure remains readable.

### HUB-006 — P2 — Endpoint save completions overwrite failed or subsequently selected drafts (new)

- Evidence: `Assets/CoreAIHub/Runtime/HubSettingsPage.cs:937` awaits saving, then unconditionally clears the typed key (`:941`), marks the endpoint as the edited one (`:943`), and reloads its stored descriptor (`:945`). ### HUB-007 — P3 — Runtime Hub adapters subscribe permanently with no release path (new)

- Evidence: `Assets/CoreAIMods/Runtime/HubIntegration/LuaCsModRuntimeHubService.cs:45` adds four runtime listeners in its constructor. The type has no disposal/unsubscribe operation. `HubModsPages.cs:72` creates a new adapter on every runtime-overload registration. Page destruction unsubscribes page-to-service handlers (`HubModsPage.cs:610`, `HubModLogsPage.cs:352`) but never the service-to-runtime handlers. The runtime exposes symmetric removal (`Assets/CoreAIMods/Runtime/LuaExecution/LuaCsModRuntime.cs:1160`, `:1176`, `:1194`, `:1224`); the session facade also retains listeners in lists (`RbxWorldPackageContracts.cs:4302`, `:4518`, `:4535`, `:4569`).
- Trigger and impact: repeatedly register/replace the Mods page or recreate Hub/binder instances against a runtime/session that survives them. Each abandoned adapter remains strongly reachable from four event delegates and continues handling runtime notifications. Retained adapters and callback work grow with past registrations instead of live Hubs. Ordinary tab switching does not create adapters.
- Confidence: high for retained subscriptions; retained bytes and event cost were not measured. Severity is P3 because the leak requires repeated adapter creation against a longer-lived runtime and does not by itself retain unsubscribed page trees.
- Existing tests: import tests (`CoreAiModsHubBinderFullTierEditModeTests.cs:950`) verify that authorized notifications reach the service. Refresh-coalescing tests (`LuaSyntaxHighlighterEditModeTests.cs:243`, `:280`) cover page-to-service callbacks, not adapter removal.

- Regression: use an `ILuaModRuntime` fake with listener counts. Register, replace/unregister, and destroy an owning binder repeatedly; counts return to baseline and disposed adapters receive no callbacks. Verify two windows sharing an externally owned service still work after either window closes.

## Observed guards and configurable seams

These are source observations, not pass claims. `IHubPage` and the registry are engine-free contracts; runtime UI and Mods.Hub assemblies are not Editor-only. Lazy page factories and the replaceable `IHubModService` allow host-specific pages/services without editing the package. `HubSettingsPage` accepts a routing controller; its legacy fallback settings path still uses the global `CoreAiBackend`/asset facade, so multi-scope legacy settings isolation was not established.
