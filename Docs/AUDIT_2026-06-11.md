# CoreAI Project Audit - 2026-06-11

> Read-only audit of main @ `66b13fd3` (v3.2.0). Two parts: Lua subsystem and general project audit.
> No critical defects were found in either part. All findings include file:line references.

---

## Part 1. Lua Subsystem (Sandbox, Pipeline, Bindings)

### Summary

The subsystem is designed well: MoonSharp is created with `CoreModules.Preset_HardSandbox | Coroutine`, dangerous globals are removed on top (`StripRiskyGlobals`), every execution chain gets `InstructionLimitDebugger` (step limit + wall-clock timeout), the envelope pipeline is protected by a sliding rate limiter, the repair loop is bounded by generations, and execution is forced onto the main thread in `AiGameCommandRouter`. Define gating (`COREAI_HAS_MOONSHARP && !COREAI_NO_LUA`) is consistent across all checked files. No critical sandbox escapes were found. The main risks are resource-related (allocation bombs such as `string.rep`, not covered by limits or tests) and Lua execution paths that bypass the rate limiter (MEAI tool `execute_lua`, coroutines).

### Critical Findings

None found. There are no direct escape vectors (access to CLR/files/processes/reflection): `UserData.RegisterType` is not used anywhere in runtime, Lua receives only `DynValue.NewCallback` wrappers over explicitly registered delegates (`LuaApiRegistry.ApplyToGlobals`, `LuaApiRegistry.cs:28-54`), and arguments are converted through `ToObject()` into primitives.

### Medium

1. **Allocation bombs are not memory-limited** - `SecureLuaEnvironment.cs:12-13`: `Preset_HardSandbox` includes the `string` module, and only `string.dump` is removed (`SecureLuaEnvironment.cs:120-130`). `string.rep('a', 1e9)` is *one* VM instruction: `InstructionLimitDebugger.GetAction` (`InstructionLimitDebugger.cs:60-74`) fires only on the *next* instruction, after a gigabyte has already been allocated. Same for `table.concat` over a growing table. Result: managed OOM / Unity GC freeze from one envelope, within the rate limit.
2. **The `execute_lua` path (MEAI tool) bypasses the rate limiter** - `LuaTool.ExecuteAsync` (`LuaTool.cs:41-88`) and `LuaLlmTool` call an arbitrary `ILuaExecutor` without `LuaGenerationRateLimiter`: the limiter is integrated only in `LuaAiEnvelopeProcessor.Process/ScheduleProgrammerRepair` (`LuaAiEnvelopeProcessor.cs:73,144`). There is no production runtime implementation of `ILuaExecutor` yet (all implementations are in tests), so the bypass is dormant, but any consumer of `LuaLlmTool` will get unlimited execution. `LUA_SANDBOX_SECURITY.md:62-73` claims "rate-limited end to end" - this does not match the tool path.
3. **`CreateCoroutine` has no limiter or total budget** - `SecureLuaEnvironment.CreateCoroutine` (`SecureLuaEnvironment.cs:60-79`); `LuaCoroutineHandle.Resume` (`LuaCoroutineHandle.cs:39-55`) resets the 10,000-step / 500 ms budget on every resume, so an infinite yield coroutine can live forever and consume up to 10k instructions every frame. `LuaCoroutineRunner` limits only the count (64), not total CPU. `Kill()` (`LuaCoroutineHandle.cs:57-90`) does not truly kill the coroutine; it only prevents resume. `Script` lives until GC.
4. **`time_set_scale` is gameplay-level DoS** - `LuaTimeBindings.cs:19`: Lua can set `Time.timeScale` to 0 or a huge value without validation; registered by default (`AggregatingGameLuaRuntimeBindings.cs:36`). This violates the documentation's own rule to "validate every binding argument".
5. **World bindings do not validate numbers** - `CoreAiWorldLuaRuntimeBindings.cs:26-47,99-109`: coordinates `(double)->(float)` without NaN/Infinity/range checks; volume without a cap; `coreai_world_load_scene` loads *any* scene from Build Settings (`CoreAiWorldCommandExecutor.cs:378-398`). Spawn is correctly limited by `ICoreAiPrefabRegistry` (`CoreAiWorldCommandExecutor.cs:98-107`).

### Low / Observations

1. `LuaExecutionGuard.Execute` (`LuaExecutionGuard.cs:36,53`) overwrites the debugger from `CreateScript` and calls `DetachDebugger()` in `finally`; reusing `Script` after the guard leaves it without limits (scripts are currently one-shot, but the contract is fragile).
2. Post-hoc `TimeoutException` after successful completion (`LuaExecutionGuard.cs:38-41`) discards the computed result; time spent inside CLR bindings is not interrupted at all (debugger fires only on Lua instructions).
3. Host exception messages leak into the model: `LuaApiRegistry.cs:50` -> `LuaAiEnvelopeProcessor.cs:112` (payload and repair prompt). The docs require error normalization (`LUA_SANDBOX_SECURITY.md:175-182`) - not implemented.
4. `result.ToPrintString()` without a cap (`LuaAiEnvelopeProcessor.cs:90`) sends a megabyte-sized string straight into `JsonPayload`.
5. `GameLuaBindingsExtensibility` (`GameLuaBindingsExtensibility.cs:13`) is a global static list: it survives the domain when Domain Reload is disabled and leaks between tests.
6. Payload parsers are resilient to garbage, but `IndexOfCommandType` can pick up `"code"` from another object later in the text (low risk); the `"```Lua"` Ordinal check in `ProgrammerLuaResponseParser.cs:19-22` is dead (shadowed by OrdinalIgnoreCase).
7. The repair loop terminates correctly (generation via `AiOrchestrator.cs:639,664`, comparison with `MaxLuaRepairRetries` in `LuaAiEnvelopeProcessor.cs:116-122`); note: one failed envelope consumes 2 limiter slots out of 20/60s.
8. Define gating - no violations found (including inline gates in `CoreAssemblyEditModeTests.cs:6-8`, `AllToolCallsPlayModeTests.cs:100-111`); `versionDefines` are correct.
9. Thread safety: main-thread marshaling in `AiGameCommandRouter.cs:56-58` + `volatile _disposed`; `LuaGenerationRateLimiter` under lock; `InstructionLimitDebugger._steps` via Interlocked.

### Test Coverage

**Covered:** removal of `io/os/debug/load/loadfile/dofile`, `require` throws, bypasses through `_G`/`_ENV`/`rawget`; `string.dump` (directly and through `('x').dump`), `getmetatable('')`, `collectgarbage`, `coroutine.close`; step limit, timeout, per-resume coroutine budget, `Kill()`, 64 coroutine limit; rate limiter (window/eviction/rejection + integration "saturated -> drop + skip repair"); repair chain E2E with generations; payload parsers.

**Not covered** (everything from the project's own "Known Attack Vectors To Test" list, `LUA_SANDBOX_SECURITY.md:163-173`):
- `string.rep` / huge tables / memory;
- deep recursion and parser bombs (`LoadString` of nested expressions);
- `setmetatable`/`rawset` on shared tables (`string`, `math`, `table`);
- `pcall` swallowing limit exceptions (`while true do pcall(...) end`);
- bindings with NaN/Infinity/extreme numbers/huge strings;
- `LuaTool`/`execute_lua` path against a real `SecureLuaEnvironment`;
- regression test for absence of `package`.

### Recommendations (Lua)

1. Wrap `string.rep` with a length cap (similar to `string.dump` in `StripRiskyGlobals`); consider other allocators.
2. Pass `LuaGenerationRateLimiter` into `LuaTool` (or the future production `ILuaExecutor` implementation), or explicitly document the bypass; fix "end to end" in `LUA_SANDBOX_SECURITY.md`.
3. Validate numeric arguments in world bindings (NaN/Inf/range, volume cap), scene whitelist for `coreai_world_load_scene`, cap/remove `time_set_scale`.
4. Add a total coroutine lifetime budget (total steps across resumes) in `LuaCoroutineHandle`.
5. Trim `ToPrintString()` and normalize error texts before publishing them to payload/repair prompt.
6. Finish tests from the list above: rep bomb, recursion, pcall swallowing, NaN arguments, `package`.

## Part 2. General Project Audit

### Summary

The project is in good shape: the `CoreAI.Core` core is genuinely isolated from Unity (`noEngineReferences: true`, no `UnityEngine` references in code), asmdef layering is correct and acyclic (Core <- Source <- Editor/Tests/ExampleGame). File-based agent memory stores are protected: `SemaphoreSlim` gate, atomic tmp+`File.Replace` write, offload to thread pool with inline fallback for WebGL. Production role magic strings have been moved to `BuiltInAgentRoleIds`/`RoleId`. API consistency is excellent (`AskAsync` primary / `AskWithCallback` convenience / `Ask` obsolete, enforced by a test). No critical defects; there are medium issues around async/logging and CI rough edges.

### Critical Findings

None found.

### Medium

1. **Copy-paste log: one message for four outcomes** - `LlmUnityAutostartEntryPoint.cs:60-99`: `"LLMUnity: autostart status changed."` is logged for "already started", exception from `agent.Start()`, warmup timeout, `llm.failed`, and success. Log-based diagnostics are impossible.
2. **`AskWithCallback` invokes callback off the main thread** - `AgentConfigExtensions.cs:118-121`: after `ConfigureAwait(false)`, continuation may run in the thread pool; using Unity API from `onDone` will throw/UB. Needs marshaling to the main thread in the Unity layer or an explicit warning in the doc comment.
3. **Stack trace lost in catch logs** - systemic pattern of `ex.Message` without `ex`: `FileConversationSummaryStore.cs:125,180,232`, `AgentConfigExtensions.cs:125`, `CoreAIGameEntryPoint.cs:112`, `LlmUnityAutostartEntryPoint.cs:70`, and more.
4. **CI: brittle sed for define** - `.github/workflows/ci.yml`, step "Strip MoonSharp": `sed 's/: DOTWEEN$/...'` silently stops working if neighboring defines change; the check does not fail on zero matches, so the "no-lua" job can silently become a duplicate of "moonsharp". Add `grep -q COREAI_NO_LUA ... || exit 1`.
5. **CI: secrets unavailable on PRs from forks** - `UNITY_LICENSE/EMAIL/PASSWORD` are empty for forks -> both matrix jobs fail on licensing. If external PRs are expected, use a skip condition or `pull_request_target` (carefully).
6. **`SemaphoreSlim _gate` is never disposed** - `FileConversationSummaryStore.cs:27`, `FileAgentMemoryStore.cs:66`: classes own an `IDisposable` semaphore but are not `IDisposable` themselves. Not critical for singletons; a handle leak when scopes are recreated.

### Low / Observations

1. Role substring heuristic in the core - `LlmConversationalRolePolicy.cs:34` (`r.Contains("chat") && !r.Contains("merchant")`); role `"MerchantChat"` is classified non-obviously. Same in `OfflineLlmClient.cs:61,81` (offline stub, acceptable).
2. File-name collisions after roleId sanitization - `FileConversationSummaryStore.GetPath`: `"A/B"` and `"A_B"` produce the same file `A_B.json`. Same in `FileAgentMemoryStore`.
3. `async void TestConnection` in editor code (`CoreAISettingsAssetEditor.cs:924`) - an exception outside try will hit the editor loop; other `async void` methods are fully wrapped in try/catch.
4. Empty catches without an intent comment: `UnityMainThreadLlmAsyncMarshaler.cs:118,135`, `RefreshOnUnauthorizedDecorator.cs:193`, `MeaiLlmClient.cs:1050,1098`, `MeaiOpenAiChatClient.cs:998,1426` (others are meaningful best-effort catches with comments).
5. CI: `unity-test-runner` sets `checkName`, but without `githubToken` the check-run is not published.
6. CI: sandbox-test coverage check through `grep -o | wc -l` over XML works, but the "10 occurrences" threshold is heuristic; parsing `testcase` nodes would be more exact.
7. Magic role strings in tests (dozens of places) are acceptable, but `BuiltInAgentRoleIds.*` would make them resilient to renames.
8. `ConfigureAwait` discipline in the core is good (45 uses); batch tool execution is sequential and correct.
9. `CoreAI.Core.asmdef` references `MoonSharp.Interpreter` - controlled through `versionDefines`/CI matrix, correct.

### TODO/FIXME in Code

Only one occurrence in the audited scope:
- `Assets/CoreAiUnity/Tests/EditMode/WorldToolEditModeTests.cs:110` - `play_sound` was removed from `WorldLlmTool`; it will be implemented separately through `IAudioController`.

### Recommendations (Project)

1. Split log messages in `LlmUnityAutostartEntryPoint` (4 outcomes -> 4 texts).
2. Marshal `onDone` in `AskWithCallback` to the main thread or document explicitly.
3. Log full exceptions (`ex`/`ex.ToString()`) at least at Error level.
4. CI: fail if `COREAI_NO_LUA` is absent after sed; consider `githubToken` for unity-test-runner.
5. Add `IDisposable` to file stores (dispose semaphore); add comments to remaining empty catches.
